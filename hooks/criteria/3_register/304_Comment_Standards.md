# **§ 304. Comment Standards and Lifecycle**

- **(a) Comment Syntax and Semantic Standards**：
    - Standard `# text` syntax MUST be used for all code comments. Writing isolation lines in code comments (for example, `# ====` or `# ----`) MUST NOT occur. Punctuation and symbol limits for code comments MUST follow § 305(g).
    - Code comments MUST maintain minimal amplitude. A code comment MUST serve only to point out non-obvious architectural reasons, system boundaries, operational limits, or design trade-offs. A code comment MUST NOT restate WHAT the source code or `git diff` already shows. Synonymous repetition and causal redundancy in code comments MUST NOT occur.
    - Using anthropomorphic, subjectively emotional, or non-engineering-quantified adjectives to describe system behavior MUST NOT occur. Function and state wording MUST be an objective description of system behavior. The objective diction requirement MUST NOT result in a restatement of WHAT the source code executes.
    - Community slang, colloquial abbreviations, and vague references MUST NOT be used in code comments. All architectural descriptions and operational acts MUST align strictly with the official documentation terminology of the target technology stack.
    - Restating a necessary result inside a single code comment by utilizing "so" in a colloquial manner MUST NOT occur.
    - Declaring the same fact more than once within a single code comment MUST NOT occur.
    - **Defensive Fluff Versus Guardrail Test**：A contrast clause of the form "instead of B" or "rather than B" MUST be classified before being written, against one criterion: whether substitution of B by a future maintainer for the documented behavior would break the contract or cause a defect. A contrast clause whose substitution would break the contract or cause a defect documents a guardrail and MUST be kept. A contrast clause whose substitution would do neither documents a defensive justification for one reasonable design option among several, and MUST be removed. The causal clause supporting the kept behavior MUST carry the full justification on its own in the guardrail case.
    - **Prohibition of the Defensive Analogy**：A comparison to a separate, already-tested case (for example "exactly like an absolute one", "just as with X") MUST NOT be used to justify why the current case receives the same treatment. The causal mechanism specific to the current case MUST be stated directly instead.
    - **Active and Passive Voice Selection**：Active voice MUST be used only where the grammatical subject is the function, method, or mechanism which itself performs the described action. Every other case, in particular a hypothetical consequence which would follow from a violation of the documented rule, MUST use passive voice or a stative construction. A causal chain of the form "would let X do A and B" MUST NOT be used.
    - **Mechanism Framing**：A code comment describing a mechanism or an invariant MUST state the mechanism as a property of the system, using a nominalized subject for the action under discussion, rather than as a chronological sequence of steps ("A happens, then B happens, then C happens"). A chronological sequence MUST be compressed into one nominalized action paired with one participial clause stating its consequence.
    - English syntactic structure, preposition placement, and word-frequency limits in code comments MUST follow § 305(e) and § 305(f) in every case.
    - If an out-of-scope and necessary correction arises due to a code change, the correction MAY be stated only in the conversation session. Writing an out-of-scope correction into a codebase comment MUST NOT occur.
- **(b) Code Comment Decisions and Lifecycle**：
    - **Default to No Comments**：A code comment MAY be written only when source code cannot express the underlying design motive. Permitted design motives include a non-obvious architectural constraint, an edge case, or a design trade-off.
    - **Prohibition of WHAT**：A code comment MUST NOT restate behavior which source code or a `git diff` already shows. Labeling an obvious algorithm with the name of the algorithm (for example, writing "a binary-tree walk is a binary-tree walk") MUST NOT occur. A session note about a code change MUST follow the same rule.
    - **Permitted WHY and Trade-offs**：A code comment MAY state only the design motive, the constraint, and the trade-off which selected the chosen path. Trade-off reasoning constitutes WHY explanations. Implementation steps constitute WHAT descriptions.
    - **Three-Line Limit and Migration**：Code comment text MUST NOT exceed three lines. An explanation which exceeds three lines, or an explanation which describes the operation of the system as a whole, MUST be migrated in full to a narrative file or a runbook. A technical document and a code comment MUST NOT contain an explanation which exceeds three lines or which describes whole-system operation.
    - **Single Claim Limit**：A code comment MUST express exactly one claim. A trade-off MAY appear in a code comment when the trade-off constitutes the single claim. A code comment MUST NOT contain a catalog of discarded designs. Syntactic compliance MUST follow § 305(f).
    - **Final Comment Language Conversion**：Temporary use of zh-TW in code comments during development MAY occur. Prior to opening an MR or PR, all code comments MUST be converted in full into English which complies with clause (b). Code comments MUST NOT contain residual Chinglish or colloquial expressions.
