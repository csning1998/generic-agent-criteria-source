# **§ 305. Style and Markings**

- **(a) Applicable Scope**：The criteria source repository is the Git working tree which publishes the clause files under `hooks/criteria/`. Every tracked file in the criteria source repository MUST satisfy the clauses which apply to the file's path glob. A clause file is not exempt from § 305(b) or from `markdown.md`. Clause (a) applies to English writing in technical documentation, MR/PR descriptions, comments, and commit messages, regardless of language medium. Dialogue follows § 301. Written English MUST follow IETF RFC Style [RFC 7322](https://www.rfc-editor.org/rfc/rfc7322) with [RFC 2119 keywords](https://www.rfc-editor.org/rfc/rfc2119) on an [ISO/IEC Directives Part 2 requirements skeleton](https://www.iso.org/sites/directives/current/part2/index.xhtml). The ISO/IEC Directives Part 2 requirements skeleton mandates one requirement per sentence. The skeleton mandates a definition placed before the rule which uses the defined term. The skeleton mandates an impersonal indicative mood. A technical document MUST state the current constraint. A technical document MUST state the chosen path. A technical document MUST state the cost of the chosen path. Theory derivation, origin history, and a full mechanism walkthrough MUST be written in a narrative file or a runbook. A technical document MUST describe only the settled architecture. A technical document MUST NOT describe the review or correction process which produced the architecture. The dialogue analog of this prohibition is stated in § 301(c)(3) and § 301(c)(4). A sentence directed at a specific past commenter is prohibited. Examples include "this corrects the prior claim that" and "a check block was considered first and rejected". The settled design MUST appear as plain fact instead. A reader with no memory of the conversation which produced the document MUST be able to understand the document fully from its own text. A term which this document binds MUST receive one definition sentence immediately before the rule which uses the bound term. Author, year, and paper type are not required for the definition sentence. Comment content and code-adjacent notes follow § 304. Non-code translation follows § 110.
- **(b) Style and Syntactic Constraints (IETF RFC Supplements)**：
    - **English Quality and Syntactic Standards**：English in technical documentation, MR/PR descriptions, comments, and commit messages MUST satisfy the following rules. Dialogue follows § 301.
        - **Semantics and Syntactic Structure**：Requirements MUST comply with the MECE principle, demonstrating high coherence and cohesion.
        - **One Requirement Per Sentence**：A sentence is the complete string range which begins at the start of a paragraph, or immediately after the preceding sentence-ending punctuation, and which continues through the next period which satisfies the end condition. The complete string range includes the period. The inspection method is the regular expression `[^。.\n]+[.。]`. End punctuation MUST be `.` or `。`. A sentence MUST NOT contain a newline. A paragraph MAY contain multiple sentences. Each sentence MUST express one requirement or one event. When two objects appear in one sentence, both objects MUST be named explicitly.
        - **Paragraph Cohesion**：Each paragraph MUST treat one topic. The next sentence MUST repeat the same subject noun or MUST name a precise noun. Fluency is produced by noun continuity inside the paragraph. Fluency is not produced by `Additionally`. `Furthermore` and `Consequently` MAY begin the next sentence after a period. `Furthermore` and `Consequently` MUST NOT attach a second independent event inside the same sentence.
        - **Prohibition of Chinglish and Pieced-Together English**：The use of Chinese-style literal translations (Chinglish) or pieced-together English syntax is strictly prohibited. The syntactic structure MUST flow naturally and conform to standard American English technical writing. Natural flow MUST NOT override one requirement per sentence. Consecutive short subject verb object sentences inside one paragraph satisfy both the fluency requirement and the one event requirement. Welding independent clauses with punctuation, with `while`, or with a participial adjunct does not satisfy either requirement.
        - **Prohibition of Punctuation-Forced Clauses**：The linking of grammatically disjointed phrases or fragments into a single sentence using punctuation (for example, semicolons, em-dashes, or commas) is strictly prohibited. A short example marker (`e.g.`, `i.e.`, `such as`, or `for example`) inside one requirement is not a punctuation-forced clause.
        - **Prohibition of Event Welding**：Event welding is the attachment of a second independent event to a sentence by a coordinated finite verb, by a participial adjunct, by a `while` adjunct, or by punctuation. Event welding is prohibited. Coordinating a second finite verb onto the same subject in one sentence is prohibited. A sentence which `renders`, `provisions`, and `deploys` before one period is prohibited. A participial adjunct which names a second event is prohibited. The form `expanding the destination allow list` after a completed clause is prohibited. A `while` adjunct which names a second event is prohibited. The forms `while registering` and `while enforcing` are prohibited.
        - **Prohibition of Colloquialisms**：The register MUST be a formal written technical documentation register. Dialogue-like or colloquial expressions are prohibited. Tutorial narration of behavior which the source code already shows is prohibited. Theory budget follows `(a)`. Comment content follows § 304.
    - **Normative Semantic Constraints (RFC 2119 Keywords)**：The semantic meaning of requirement keywords in all documentation and comments MUST comply with the definitions in RFC 2119.
        - `MUST` indicates a mandatory requirement.
        - `MUST NOT` indicates an absolute prohibition.
        - `SHOULD NOT` indicates a strong recommendation against an action unless overridden by unavoidable physical constraints.
    - **Prohibition of Preposition Stranding**：Prepositions MUST NOT be placed at the end of any independent or subordinate clause. Formal relative clauses MUST be used (for example "in which execution runs" is required, and sentence-final "execution runs in" is prohibited). The weight of this clause takes priority over the other register goals within `(b)`. If literal compliance with this clause conflicts with other register requirements (for example, natural fluency or avoidance of colloquialism), this clause controls in every case, and the conflict MUST be resolved by rewriting into an agentless or passive construction.
    - **Vocabulary Frequency Limit**：Scope and criterion MUST follow § 302(d). Permitted vocabulary includes standard formal terms up to the C1 frequency tier (for example, `utilizing`, `prior to`, and `consequently`). Prohibited vocabulary includes rare synonyms (for example, `ameliorate` instead of `improve`), archaic connectives (for example, `henceforth` and `whereby`), and colloquial substitutions with a formal equivalent (for example, `too` in place of `also`, or a dynamic-verb use of `runs` in place of `is executed`).
    - **Impersonal Tone**：First-person pronouns (`I`, `we`, and equivalents) MUST NOT be used. `this`, `that`, `it`, `where`, a non-relative `which`, `them`, `those`, and `these` MUST NOT occupy the subject or object position of a clause. The possessive `its` MUST NOT replace a repeated noun across a sentence boundary. A demonstrative determiner immediately followed by an explicit noun (for example `this test`, `that symlink`) is not a demonstrative pronoun and MAY be used, because the following noun names its own referent. A vague deictic reference (for example `pointing there`, `the protection here`) MUST NOT be used even where the referent is grammatically recoverable. The actual referent MUST be named instead.
    - **Relative Clause Formation**：A relative clause MUST use `which`, `in which`, or `whose`. `that` MUST NOT introduce a relative clause, including a restrictive relative clause, because a relative pronoun is already bound to an explicit antecedent and carries no ambiguity for `which` to resolve. A reduced relative clause, meaning a relative clause whose relative pronoun has been elided (for example "the state a resource holds"), MUST restore the elided relative pronoun. A detail which is not a second event MUST attach as a `which`, `in which`, or `whose` relative clause on a noun which already appears in the same sentence. Opening a new independent clause for the detail and joining the new clause with a semicolon is prohibited.
    - **Disambiguation of `that`**：The English token `that` has three uses. A relative pronoun `that` is prohibited. A complementizer `that` which introduces a content clause is prohibited in technical documentation, MR/PR descriptions, comments, and commit messages. A demonstrative determiner `that` is permitted only when an explicit noun follows immediately in the same noun phrase. Across a sentence boundary the explicit noun MUST be repeated. A metalanguage mention of the token `that` inside backticks is not a use. A quotation of a prohibited sentence MAY retain `that` inside the quotation.
    - **Since and Because Selection**：A causal clause introduced by `since` MUST describe an existing stative condition, indicated by a copular verb (`is`, `are`) or a passive construction containing a form of `be` (for example `has been written`, `can be recovered`). A causal clause introduced by `because` MUST describe a dynamic action, indicated by a non-copular main verb (for example `injects`, `carries`, `resolves`). A comma MUST NOT precede `since` unless the clause preceding `since` itself contains an enumeration of two or more items or two or more coordinated clauses.
    - **Prohibition of the Escape-Hatch Adverb**：`so` and `otherwise` (including `would otherwise`) MUST NOT be used to imply an unstated counterfactual. The condition on which the clause depends MUST be named explicitly instead.
    - **Prohibition of Bare Negation**：A finite main clause MUST NOT negate an object using a bare `no` (for example `declares no default`). The main clause MUST use `does not` plus the verb instead (for example `does not declare a default`). A non-finite participial phrase modifying a noun (for example `leaving no dangling separator`, `with no diagnostic`) is not a finite main clause and MAY retain a bare `no`.
- **(c) Markings and Formatting Standards**：
    - **Prohibited Symbols**：dashes (`-`), em-dashes (`—`), en-dashes (`–`), and arrow symbols (`→`, `←`, `⇒`, and equivalents) are prohibited in prose in every case, corresponding to § 302(c). Math spans delimited by `$` and fenced blocks whose language is `mermaid` MUST follow `markdown.md`. A hyphenated compound in running prose is prohibited. The forms `allow-list` and `first-match` MUST be written as `allow list` and `first match`. A backticked identifier MAY retain a hyphen which the identifier already contains.
    - **Giant Parenthesis Limit**：A second independent sentence MUST NOT be wrapped in parentheses after another sentence. The secondary material MUST be formatted as a separate sentence. Short supplements MAY stay in parentheses. Permitted short forms include example markers (`e.g.`, `such as`), brief glosses, and `i.e.` restatements of a nearby term. A parenthetical which could stand as an independent clause is prohibited.
    - **Process Descriptions**：Sequential processes MUST be described using words. Symbol chains in prose are prohibited.
    - **Colon Use**：Colons (`:`) MAY introduce a list, an example, a definition, or a standard URL prefix. A colon MUST NOT join two independent sentences into one sentence.
