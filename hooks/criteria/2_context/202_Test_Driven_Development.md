# **§ 202. Test Driven Development**

§ 202 applies when the owner or project documentation declares the repository a TDD repository. § 202 covers production and test mutations in Python, TypeScript, and Go trees which the declaration covers. § 202 covers HCL only in Terraform configurations and YAML only in Ansible playbooks only when a corresponding automated test file exists for the targeted path.

- **(a) Production Code Write Constraints**：Production code mutations during TDD are governed by three mutually exclusive development contexts.
    - **(1) Red Step Scaffolding**：Prior to owner authorization into the green step, production code mutations MUST be restricted strictly to type declarations, interface definitions, and empty function stubs necessary for test compilation. Writing business logic, control flow, or algorithms inside production code prior to green step authorization is strictly prohibited.
    - **(2) Green Step Implementation**：Writing business logic, control flow, and implementation algorithms MUST occur only within an authorized green step.
    - **(3) Refactoring of Passing Code**：Structural refactoring of production code covered fully by passing automated tests does not require a failing test prerequisite. Structural refactoring MUST preserve passing execution across the automated test suite.
- **(b) Execution States and Gate Transitions**：Automated test execution results are evaluated across four mutually exclusive states prior to gate advancement.
    - **(1) Valid Red Result**：A valid red result is an execution in which the test suite and production code pass compilation and static type checks, existing tests remain passing, and only assertions targeting missing behavior produce runtime failures. Only a valid red result MAY advance to presentation and gate authorization.
    - **(2) Static or Tooling Failure**：A static or tooling failure is an execution exhibiting a compilation error, a static type checking defect, a syntax error, a missing module import, or a test runner crash. The system MUST resolve the tooling defect or MUST supply minimal compilation stubs before re evaluating execution state.
    - **(3) Regression Defect**：A regression defect is an execution in which assertions targeting missing behavior fail and previously passing tests also fail. The system MUST eliminate regression damage prior to gate advancement.
    - **(4) Premature Green Execution**：A premature green execution is an execution in which the test suite completes without assertion failures. A premature green execution demonstrates existing targeted functionality or absent verification coverage. Writing production implementation code based on a premature green execution is strictly prohibited.
    - **(5) Batched Matrix and Gate Transitions**：A failing test presentation MAY present a batched red matrix covering multiple cohesive test cases within one test suite file. Advancing into the green step MUST require explicit authorization from the owner. Transitioning a batched red matrix into passing execution MUST proceed incrementally by cohesive business logic units. For each business logic unit, test execution MUST demonstrate passing status for targeted assertions, expected failure for remaining matrix assertions, and zero regression across existing automated tests. Authorization for production implementation writes MUST be scoped to each business logic unit until the complete matrix transitions to passing execution.
- **(c) Pre Presentation Lint**：Prior to presentation of a failing test result, every project linter which applies to a test file modified in the same step MUST pass. A lint failure MUST be resolved in the same step. Presentation of the failing test result MUST NOT occur while a lint failure remains.
- **(d) Post Authorization Verification**：After the owner authorizes progress into the green step, the system MUST re execute the minimal automated test set which covers the change. The system MUST re execute every applicable project linter in the same turn. Reporting MUST follow § 111.
- **(e) Hygiene and Authorization**：Hygiene work which the repository already declares（linter repair, formatter repair, and equivalent local verification repair）MUST be completed by the system. Asking the owner whether to perform that hygiene work MUST NOT replace completion of the hygiene work. A mutation outside the authorized duty MUST NOT proceed. The system MAY ask a clarifying question. The system MUST NOT begin a mutation until the owner has given explicit authorization for that mutation.
