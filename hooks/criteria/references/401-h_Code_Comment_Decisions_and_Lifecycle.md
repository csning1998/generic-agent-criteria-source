# **§ 401(h). Code Comment Decisions and Lifecycle**

- **(h) Code Comment Decisions and Lifecycle**：
    - **Default to No Comments**：A code comment MAY be written only when source code cannot express the underlying design motive. Permitted design motives include a non-obvious architectural constraint, an edge case, or a design trade-off.
    - **Prohibition of WHAT**：A code comment MUST NOT restate behavior that source code or a `git diff` already shows. Labeling an obvious algorithm with the name of the algorithm (for example, writing that a binary-tree walk is a binary-tree walk) MUST NOT occur. A session note about a code change MUST follow the same rule.
    - **Permitted WHY and Trade-offs**：A code comment MAY state only the design motive, the constraint, and the trade-off that selected the chosen path. Trade-off reasoning constitutes WHY explanations. Implementation steps constitute WHAT descriptions.
    - **Three-Line Limit and Migration**：Code comment text MUST NOT exceed three lines. An explanation that exceeds three lines, or an explanation that describes the operation of the system as a whole, MUST be migrated in full to a narrative file or a runbook. A technical document and a code comment MUST NOT contain an explanation that exceeds three lines or that describes whole-system operation.
    - **Single Claim Limit**：A code comment MUST express exactly one claim. A trade-off MAY appear in a code comment when the trade-off constitutes the single claim. A code comment MUST NOT contain a catalog of discarded designs. Syntactic compliance MUST follow `(f)`.
    - **Final Comment Language Conversion**：Temporary use of zh-TW in code comments during development MAY occur. Prior to opening an MR or PR, all code comments MUST be converted in full into English that complies with clause (h). Code comments MUST NOT contain residual Chinglish or colloquial expressions.
